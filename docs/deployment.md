# 裸机部署

## 暂停 / 恢复整机 Agent 监控

设备总览 → 机器管理 → 展开受管机器，每台未删除机器有「暂停监控 / 恢复监控」。这是暂停采集，不是软删除、断开 SSH 或停止服务；无需重新输入 SSH 凭据、重新部署或更换 UUID。原权限、历史及身份保留，用户/权限检查独立开关也保持原设置。

新版 Agent 收到版本化指令后将状态写入私有 SQLite，释放采集器并取消后台扫描任务，不再采集、实时上报或发送离线队列；已开始的有界只读任务可能收尾，但结果丢弃、不再调度。仅每 60 秒发送一次经原 Agent token 鉴权的轻量控制请求，应用状态时另发一次确认；SSH-only 保留已有长连接及必要保活，不重新登录。控制请求不更新指标时间、在线心跳或历史，不补零。暂停期间网络统计保留最后一份 Agent 快照，平台侧仍计控制流量。

「恢复监控」在下一次控制检查生效，通常最多约一分钟加网络/采集耗时；网络断开则等待连通，不冒充已恢复。恢复会重新创建采集器并生成新样本。暂停意图及确认持久化于平台数据库；Agent 本地也持久化，重启时先读控制状态再创建采集器。平台/Agent 重启、SSH 重连不会自动解除暂停。

页面区分待确认、已暂停/控制连接离线、恢复待确认及等待新指标。旧 Agent 不支持本协议时提示需更新，不将保存设置等同于采集已停止。先更新平台及数据库迁移 `0011`，再更新 Agent。暂停节点不可重新部署；应直接恢复。页面操作沿用内网同源校验、原机器 ID 确认及版本并发检查，记录审计，不增加 SSH 操作或额外提权。

旧版 Agent 从未支持/确认控制协议时，显式恢复监控后，平台仍根据真实的新鲜心跳显示在线并接收实时指标，不要求其发送不支持的控制确认；不会伪造已应用版本。已确认过控制协议的新版 Agent 仍需收到对应恢复版本的新指标，不能用缺少控制字段的旧快照绕过等待。

## 按机器暂停用户状态采集

「用户状态」每台机器标题右侧有独立采集开关，默认开启，设置保存在 PostgreSQL。关闭后，新版 Agent 在下次成功完整上报后停止用户状态专用的 `who` / `loginctl`、用户组、Shell 状态及用户进程计数采集，停止上报用户列表；不关闭 CPU、GPU、磁盘、网络及独立权限检查。权限检查、工具发现和共享进程扫描仍可能读取必要的基础账户、UID / home 信息，不等于全局禁用账户访问。已有历史不会删除；页面关闭时不展示旧用户快照，并区分已确认、等待应用、离线和旧版 Agent 需更新。

Agent 将已应用的开关保存在自身 SQLite，重启时先读取再进行首次扫描；恢复开启会重新采集，不复用旧状态。部署顺序为先更新平台（包含 `0009_node_user_collection.sql` 新表迁移），再更新需要此功能的 Agent。旧版 Agent 仍能上报，但不能停止采集；不能仅更新前端。迁移不改写历史，不改变任何服务权限，生产环境须在授权的更新窗口执行。

## 按机器暂停权限检查采集

「权限检查」每台机器标题右侧有独立开关，默认开启，与「用户状态」采集开关互不影响。关闭后，新版 Agent 在下次完整上报成功后停止权限检查调度，丢弃待处理任务及当前缓存，后续不再执行该类目录、ACL、sudo / root 规则检查，也不再上报旧权限审计；不会修改真实账户或文件权限，CPU、磁盘、网络等采集继续运行。

开关分别持久保存在平台 PostgreSQL 和 Agent SQLite，重启后首次扫描前读取；离线节点等待上线应用，旧版节点提示更新 Agent。页面关闭时不把旧快照展示为当前，也禁止对暂停的证据新增人工 OK。已有人工标记保留但暂停显示，重新开启后需取得新审计；新证据与原标记不同仍自动失效，历史审计日志保留。升级顺序为先更新平台（`0010_node_permission_collection.sql` 新表），再更新需要此功能的 Agent；生产更新需另行授权，不会仅因修改代码自动重启生产服务。

## 按机器关闭代理监控

「Global Network · 代理」每台机器标题右侧有独立的「代理监控采集」开关，默认开启。关闭后，新版 Agent 在下一次完整上报/控制同步后停止代理识别、监听套接字表和代理进程文件描述符扫描，清空代理观测，不再上报旧代理实例；不会停止实际代理、修改代理配置、账户或 SSH，也不影响 CPU/GPU/磁盘、用户、权限检查和 Agent 工具。部分进程枚举仍为用户和工具发现共用，并非停止全部进程访问。

平台和 Agent 分别持久保存开关，重启前首次扫描即读取；重新开启需要新扫描，不恢复旧缓存。关闭机器的旧代理快照不展示，也不参与代理数量、用户、监听和端口冲突统计。页面区分等待确认、离线、旧 Agent 需更新；旧平台缺少该字段时明确提示更新平台，不将灰色开关当成已关闭。整机监控暂停时应先恢复整机监控，单独开启代理不会解除整机暂停。

升级必须先更新平台（包括 `0012_node_proxy_collection.sql`），再更新 Agent。报告和轻量控制分别按能力协商代理开关，避免给旧 Agent 的严格策略结构发送不支持的字段。迁移短时锁表且设 2 秒锁等待上限；仅在授权的生产更新窗口应用。本次代码修改不会自动部署或重启生产服务。

## 网络资源分析

「平台 → 网络资源分析」按固定分类展示主进程的 HTTP 正文接收/提交、请求发起/结束/失败/进行中次数，Gitea/自检请求、WebSocket 终端、SSH 新 TCP/握手、命令/终端通道、SCP 及隧道统计。Agent 将其注册、完整上报、实时上报三个 HTTP 客户端分类随原有完整心跳上传，不增加心跳或 SSH 数量。计数为常量大小原子内存数据，仅最新快照随原有机制保存，不逐请求写数据库、不抓包；未采集内容、URL、鉴权头或秘密。

这是**本次进程累计**，不是 24 小时历史。每 15 秒按相邻两个真实采样求速率；首次、重启、过期重复样本、回退和离线不补零。重启清零，以 PID 和统计起点区分；旧 Agent 未支持时显示未知。发送正文尤其是 Agent 项表示提交给客户端的尝试预算（含失败和重试），不保证已在线路发送。平台仅统计实际消费的请求正文及交给传输层的响应正文；不含 HTTP 头、TLS/SSH/TCP/IP 开销、重传及数据库线路字节，不等于整机网卡或内核进程 socket 字节。子进程部署脚本不在主进程计数范围。

SSH 由平台发起，新连接计数只在真正发起 TCP/握手时增加，复用 exec/SCP/终端通道不增加新登录次数。存活连接为平台持有的连接对象数；失败/取消含失败和中断尝试，并非管理员审计认证结果。SSH 命令/上传统计通道读写，不含被忽略的 stderr、命令协议和保活；隧道统计内层 TLS 字节，不含 SSH 外层。HTTP、Agent 与 SSH 各层可重复观察同一批数据，**不可跨层相加**。页面自己的轮询也计入平台请求开销。数据库不可用时仍可读本地平台计数，节点部分明确不可用。需要更新平台及希望显示新计数的 Agent；不会因修改代码自动部署生产。

## 更新平台本身

「Agent 管理 → 平台自身更新」可安装已发布的后端、前端和手册候选，并只重启平台服务，不更改 Agent 身份或 Full / Basic 权限。先以平台普通用户执行 `./scripts/run-server.sh --build`，或对已有构建执行 `--publish-platform`。网页不自动构建或拉取 Git，未发布/已是候选版本时按钮禁用；第一次使用需先手动部署含此功能的平台版本。

点击更新需同源 HTTPS、可信本机 SSH 主机密钥、管理员 SSH/sudo 验证，并确认短暂离线与数据库备份。平台使用独立任务安装并核验 HTTPS/数据库就绪，页面展示结果，成功后可载入新版；失败尝试回退平台文件，**已执行的数据库迁移不会回退**。标准 Linux 普通用户布局下，保留平台自身目录、清单及候选文件的权限检查，但允许 home、`.local` 等上级目录组写入，不再因此禁用添加机器或平台更新。该内网兼容策略不防范同机组成员替换上级目录，不自动修改生产权限。详见源码中的 `deploy/linux/operations/README.md`。

## 从设备总览添加机器

设备总览的“机器管理”支持添加、编辑显示名称/备注、软删除与恢复。新机器无需预装 Agent：填写内网 IP、SSH 端口和用户名，选择运行权限及密码或 SSH 私钥鉴权，并独立核验首次 SSH 主机指纹；确认后平台通过 SSH 下发最新已发布 Agent、安装并启动，页面展示部署进度与日志，并等待对应权限的首次心跳。默认自动检查目标到当前页面 HTTPS 地址的连通性；失败时使用 SSH 长连接，也可明确选择仅直连或仅 SSH。私钥支持 OpenSSH / PEM（最大 12 KiB）及解密口令，不接受 `.pub` 或 `.ppk`。目标需 Linux、Python3 及与 ELF 候选匹配的架构；Full 还需要 systemd。新增机器入口仍拒绝覆盖已有 Agent 配置/状态；已有机器可使用原节点的「重新部署」覆盖修复或「SSH 长连接」接管，不新增机器身份。

- **普通用户 Basic（默认）**：SSH 账户必须是非 root 且 home 为 `/home/账户`，只要求 Linux、Python3 和匹配的 CPU 架构，不再要求预先启用 linger。有可用用户 manager 且 linger 已启用时优先安装 systemd 用户服务；否则自动安装普通用户兼容守护进程。程序、配置和 SQLite 状态库统一位于 `~/.easymanage/`，临时安装包位于其中的 `staging/agent.XXXXXXXX`；使用 systemd 时单元仍在标准的 `~/.config/systemd/user/`。不调用 sudo、不写系统安装目录、不主动修改 linger/logind；后续可从设备总览提权为 Full。
- **管理员 Full（首次直接安装）**：支持 SSH root（home 为 `/root`）或有 sudo 权限的普通 SSH 账户；不要求用户 manager / linger，不先运行 Basic。密码登录时 sudo 密码留空默认复用 SSH 密码；密钥登录可另填 sudo 密码，免密 sudo 可留空。固定安装器经管理员验证后，将程序安装到 `/usr/local/sbin/easymanage-agent`、配置到 `/etc/easymanage/`、状态到 `/var/lib/easymanage-agent/`，创建 root 系统服务并启用开机启动。安装前重新检查已有身份，校验二进制/CA/配置摘要；服务启动失败时尝试撤回本次新增服务和文件并保留恢复数据，不承诺网络中断后的完整回滚，不重启整机。

### 原机器的覆盖修复与重新部署

展开机器管理中的受管列表，点击原机器的「重新部署」，确认按原机器 ID 覆盖修复并重启 Agent。该入口支持残留安装和已卸载的机器，提交时需超过在线判定窗口、未暂停、未软删除且存在可信 SSH 登记；平台本机受保护。地址、账户、主机公钥、机器 UUID 及原 Basic / Full 级别均由后台原记录确定，不能通过请求修改，也不会将原 Full 降为 Basic。软删除的机器应先恢复；仍在线的机器请使用更新/重启。

可选择密码、私钥或本浏览器已获准使用的加密保存凭据，以及自动、仅 SSH、仅 HTTPS 网络方式。安装和文件上传复用 SSH 通道，已有正常隧道可直接复用；每目标仍最多三条连接。同一 UUID 的现有程序、配置和服务允许覆盖；安装前校验现有配置及 SQLite 的节点身份和固定状态路径，备份原程序/配置，停止本 Agent 后创建包含 WAL 已提交数据的一致 SQLite 恢复副本。正式数据库原地保留，机器 ID、未上报队列、采集开关及其他元数据不重置；仅授权重装时重新签发 Agent 连接凭据，恢复失效旧凭据的机器。不重启整机、不强杀其他 Agent。

若发现不同 UUID、不可读/损坏的身份库、符号链接、不安全所有权、自定义状态库路径或 Basic / Full 冲突，会在覆盖前明确拒绝，不能为了安装而丢弃原历史。Full 修复使用平台内嵌的固定 root 安装器，不执行用户可改写的暂存脚本；启动失败时尝试恢复旧程序/配置和原服务状态，数据库不回滚或删除。Basic 同样保留原 SQLite 并尝试恢复旧文件/服务。网络中断不保证自动回滚，应核对保留的恢复目录。已卸载的私有归档不被自动扫描或移动，只有当前标准安装路径下的数据自动保留。

重新部署下发最新候选、原 UUID 和该节点专用的十分钟一次性注册凭据，页面展示新任务进度与脱敏日志。平台不新增节点、不删除历史、显示名称或备注；在一致备份后仅移除 SQLite 的旧 `agent_token` 元数据，让新进程使用单机凭据重新注册，其他表及元数据不删除。注册成功后旧 token 失效。必须确认安装开始后的新注册及真实新采样，且来自不同于旧快照的新进程并符合原 Basic / UID 或 Full / UID 0 才标记成功，旧缓冲心跳不能充当成功证据。启动失败回退时，若尚无新 token，仅尝试从备份恢复旧 token，不覆盖已签发的新 token。失败时保留原记录、历史和恢复包。已完成任务重试时只轮换临时日志访问凭据，不会替换仍在运行的任务。

### 仅开放 SSH 端口的机器

新增机器可选择「自动」「SSH 长连接」「仅 HTTPS 直连」。自动模式在部署时通过同一个 SSH 控制连接，以目标视角验证 HTTPS 地址及 CA；不可达或校验失败时建立 SSH 通路。已有安装使用机器管理中的「SSH 长连接」切换/重连，不重新安装、不生成新 UUID。初次指纹检查的握手最多缓存 60 秒，部署会复用它；旧版可信清单默认继续直连，不会自动迁移生产节点。

每个目标 IP/SSH 端口最多 **3 条真实 SSH TCP 连接**（包括握手中的连接）：

| 连接 | 用途 |
| --- | --- |
| 控制连接（常驻） | 复用 exec/SCP 通道执行安装、更新、重启、查询与终端；操作串行，繁忙时返回提示，不新建短连接 |
| 上报连接（常驻） | SSH 远程回环转发，承载 Agent 注册、完整指标、实时指标、策略响应；不为每个采样重新登录 |
| 附加身份（按需常驻） | 不同管理员/鉴权方式的运维连接；同一凭据复用，不允许第四条连接 |

平台主动连接目标 SSH 端口，目标 Agent 只访问其 `https://127.0.0.1:远端回环端口`。TLS 字节经 SSH 转发到平台固定的回环 HTTPS 监听；平台私钥绝不下发，CA 和主机名校验不跳过。因此平台自身 HTTPS 必须在 `127.0.0.1` 可达，证书 SAN 必须包含 `127.0.0.1`。隧道不监听远端外部网卡；建立及每次重连都会核对 `/proc/net/tcp{,6}` 的实际监听，拒绝被 `GatewayPorts=yes` 扩大为全网卡的监听。无需 4090 回连平台的 8443。

管理员必须允许当前账户的 SSH **远程回环转发**；`AllowTcpForwarding`、`DisableForwarding`、`PermitListen`、authorized_keys 限制等均可能禁止它。拒绝时明确报告，不修改 sshd、防火墙、路由或绕过管理员限制。相关语义见 [OpenSSH sshd_config](https://man.openbsd.org/sshd_config)。机器健康检查复用连接池状态，SSH 模式不再额外探测 TCP 22；CLI fleet 分发器不是该连接池的入口，不应同时手动对这些目标运行其他 SSH 客户端。硬上限约束本平台进程，不能限制管理员或其他程序自行创建的 SSH 连接。

SSH 验证成功后，平台将密码、私钥、私钥口令及必要的 sudo 口令以 **AES-256-GCM** 认证加密存入可信清单同目录的 `ssh-vault/<节点 UUID>.enc`。每次写入使用随机 nonce；认证附加数据绑定节点 UUID、SSH 地址/端口、账户及已核验主机公钥，拒绝篡改、替换机器或密钥。专用随机 256 位主密钥为 `ssh-vault/master.key`，目录 `0700`，文件 `0600`，仅平台账户可读；不借用 TLS 私钥，不向目标下发主密钥。主密钥丢失时不会自动换钥覆盖现有密文，应恢复备份或由管理员重新录入；备份主密钥应与密文分开、离线保管。整个保险库必须排除版本控制、公开文件服务和日志。

原验证浏览器得到节点专用、有效 30 天的 `Secure; HttpOnly; SameSite=Strict` 使用凭证，只用于请求平台使用保存的凭据，无法读取密码或私钥。新浏览器、凭证过期或浏览器 Cookie 被清除时需验证一次 SSH，防止内网中任何知道 UUID 的人直接使用已保存凭据；不会保存浏览器 localStorage 中的密码/私钥。SSH 身份验证成功但后续网络切换失败时仍保存密文及浏览器使用权，下一次可直接重试，并返回固定脱敏的失败原因，不回显远端输出。

平台重启后，只恢复此前成功启用、未软删除、仍有有效私有配置的 SSH 隧道，使用原远端回环端口，不重装或修改 Agent 身份、服务权限及远端配置。手动「断开」暂停自动恢复并保留密文；「断开并删除平台保存的凭据」移除该节点密文，保留远端 Agent 和身份。软删除暂停自动恢复，恢复节点后需手动重连。正常监控不需要重复输入 SSH 密码或私钥。应用层每 15 秒检查保活，SSH keepalive 间隔 30 秒；**断线后每隔 60 秒重试一次，连续失败最多 3 次后停止并显示原因，等待手动重连**。平台启动恢复先立即尝试一次，失败后间隔 60 秒，总共最多尝试 3 次；主机密钥变化或鉴权失败立即停止，不轮询错误密码。重建前释放旧连接，继续遵守最多三连接限制。

磁盘加密不防御已控制平台账户或 root 的攻击者：自动恢复要求平台进程能解密，运行时自有明文缓冲区尽量清零，但 SSH / TLS / 操作系统内部副本不承诺完全擦除。平台页面自身没有通用登录系统；节点浏览器使用凭证及下述独立管理员凭证不代替平台网络访问控制。请限制平台访问范围并保护平台账户。网络不可用期间数据仍按 Agent 原有 SQLite 队列缓冲。

### 管理员凭据复用

Agent 更新、重启、提权，以及平台更新/应急重启支持密码或 SSH 私钥鉴权。首次操作先通过可信主机密钥校验、SSH 登录和固定只读 root 权限检查，全部成功才保存。私钥口令与独立 sudo 密码一并加密，支持 sudo 免密；不会执行任意用户输入的命令，也不会把凭据作为进程参数、明文临时文件或 Agent 配置下发。鉴权失败不覆盖既有记录。

每机器保存当前一套管理员身份，密文为 `ssh-vault/admin-<UUID>.enc`，AES-256-GCM、随机 nonce、目录/文件权限及主密钥保护与 SSH 保险库一致；加密附加数据另有管理员角色域，绑定机器 UUID、地址/端口、原部署账户和可信主机公钥文件。它不会覆盖普通用户的 `<UUID>.enc`，普通 SSH Cookie 不能用于管理员操作。更新平台与更新平台本机 Agent 复用同一机器的管理员身份。

验证浏览器得到独立的 `Secure; HttpOnly; SameSite=Strict` Cookie，不得到密码、私钥或口令。后续选择“使用平台已加密保存的凭据”，平台解密并执行原有 SSH/sudo 校验，无须再次输入。浏览器授权有效期 30 天，成功验证复用时续期而不轮换当前能力令牌；新管理员鉴权会撤销旧授权。换浏览器、清除 Cookie、过期、凭据失效或主机密钥/绑定信息变化需要重新验证。重启平台仍保留密文和授权，不依赖数据库可用性。

对话框内“清除已保存的管理员凭据”只删除管理员密文并撤销浏览器授权，保留普通用户 SSH 长连接、Agent 身份和历史。该入口不是卸载、降权或停止服务。所有状态响应只返回是否可复用，错误与日志不包含凭据；HTTPS 证书仍需可信，不能用内网环境替代证书和主机密钥校验。

已有 Basic 切换会备份私有 `agent.env`、改写 URL 并重启原用户 Agent；已有 Full 需 root/sudo 授权修改原 Full 配置，保留原权限/SQLite 身份并重启 Full。尚未注册且凭据已过期时，仅续发原 UUID 的单机一次性凭据，不下发平台通用注册密钥。切换接口返回「等待心跳」而不是「部署成功」，是否恢复以实际新上报为准。断开只关闭 SSH 通路，不卸载 Agent；软删除还停用上报凭据，恢复后须显式重连。

### 无 linger 的普通用户兼容模式

`~/.easymanage/bin/agent-user-control.py` 以 SSH 用户运行独立后台 Python 守护进程，启动并在崩溃后重启 Agent。后台进程关闭 SSH 的标准输入/输出并建立独立会话；锁由 Agent 一并持有，避免守护进程意外退出后产生重复采集器。日志在 `~/.easymanage/logs/agent.log`，最多保留两个各 1 MiB 的文件。该模式额外常驻一个 Python 进程，不视为系统服务。

若允许用户 crontab，安装器仅新增/替换 `EasyManage Agent compatibility` 标记块，保留其他用户任务；通过 `@reboot` 与每分钟检查恢复守护。不开启或配置系统 cron 服务，是否执行依赖目标机 cron 实际运行及账户策略。无法读取 crontab、禁止使用或没有命令时，不阻断首次安装，任务日志会明确提示无法保证开机/会话退出后的自动恢复。禁止把这种情况显示为完整开机自启保证。[logind 的会话清理策略](https://github.com/systemd/systemd/blob/main/man/logind.conf.xml) 仍可能回收后台进程，普通用户模式不会绕过管理员限制。

手动控制：`python3 ~/.easymanage/bin/agent-user-control.py restart`（或 `status`、`stop`）。`stop` 会禁用恢复标记，cron 不会擅自重新启动；再次显式 `start` 可恢复。提权会先以原用户停止兼容守护并禁用恢复标记，确认退出后才复制 SQLite 身份；Full 启动后不会被 cron 拉回 Basic。提权失败时尝试恢复此前启用的兼容实例。

平台服务用户需有安全可写的可信清单目录，配置 `EASYMANAGE_OPERATIONS_TARGETS`。浏览器管理的增量存 `managed-targets.json`，不会覆盖原 fleet 清单；每机器已确认的 SSH 公钥存同目录独立 `.known_hosts` 文件，均不入 Git。设置 `EASYMANAGE_AGENT_CA_CERTIFICATE` 指向 Agent 信任的 CA（默认平台证书同目录 `ca.crt`），候选默认来自平台用户已发布的 `~/.easymanage/releases/current/target/release/easymanage-agent`。系统模式平台可用 `EASYMANAGE_AGENT_RELEASE_ROOT` 指定经批准的发布目录。 目前页面不改 SSH 地址/用户名；新机器未配置 SSH 免密分发时，现有依赖免密的 Basic 更新/重启功能不会冒充可用，后续仍可用管理员凭据提权。

部署任务显示阶段、百分比和受控日志，上传、SHA-256 校验、服务启动后必须确认真实 Basic / SSH 用户 UID 或 Full / UID 0 心跳才标成功。SSH / sudo 密码、私钥及口令仅以保险库密文保存，不写数据库、普通配置、浏览器存储或任务日志；输入框提交/切换模式时清空，不展示私钥正文。浏览器到平台通过 HTTPS 加密，平台到目标通过 SSH 加密；必须验证平台证书和目标指纹，忽略证书告警会削弱防中间人保护。平台使用内存私钥 API 签名，不创建明文临时私钥文件、不把私钥或 sudo 密码作为进程参数、不把 SSH 凭据下发给 Agent。管理员 sudo 口令不进入常驻连接 worker，仅在需要修改已有 Full 配置时由受控请求使用。错误响应和日志使用固定脱敏消息，不回显请求中的凭据或 SSH 原始错误。

网络切换保留原配置私有备份；支持 `export KEY=...`、带引号的节点 ID 以及仅在 SQLite 元数据中保存 UUID 的旧安装。只读确认 SQLite 身份后才补齐配置，不创建新数据库或轮换 Agent token。缺少安装文件、权限/所有者不符、CA 不一致、UUID 不匹配、Full 服务不匹配、配置重复项及写入失败均分别报告。已卸载的目标不能仅通过网络切换恢复安装，应使用原机器的「重新部署」，不能把这个错误当作 SSH 端口不通或跳过身份检查。

新机器仅获得单机、10 分钟、一次性注册凭据。任务能力凭据只留当前页面内存，日志最多保留 30 分钟；关闭页面不取消服务端任务。失败保留机器 ID 和必要的私有暂存包，可能已经创建用户/系统服务，不能盲目重新安装新身份。

软删除保留历史指标、机器 UUID、Agent 凭据哈希和远端文件，不卸载服务、不删除身份库。平台停用上报凭据、拒绝该 UUID 重新注册并从当前监控隐藏；恢复重启用原凭据，等待新心跳。历史仍受正常保留周期管理。改/删/恢复需该机器登记用户或管理员 SSH 鉴权；目标离线可通过平台本机可信管理员 SSH/sudo 鉴权。平台本机节点有删除保护。编辑名称不会被后续 Agent 原始主机名上报覆盖。

当前只支持 Linux 裸机部署，不使用 Docker。系统级服务位于 `deploy/linux/system/`，普通用户部署位于 `deploy/linux/user/`，两种模式均有效。Windows/macOS 准备目录只放接入说明，尚无可运行安装器。部署前核对服务状态、目标用户、SSH 主机密钥和磁盘空间；目录整理不自动迁移现有服务。

以平台普通 SSH 用户在仓库根目录构建：

```bash
./scripts/run-server.sh --build
```

该命令构建 Server、Agent、React 控制台和 VitePress 文档；不会立即重启运行中的服务。已初始化的平台还会发布供网页分发的 Agent 候选版本。

已有普通用户部署可按需执行以下命令（不是系统级安装命令）：

```bash
./scripts/run-server.sh --fleet
./scripts/run-server.sh --status
```

`--fleet` 会更新并短暂重启用户 Server 与 Basic Agent，已启用的 Full 保持管理员权限边界。数据库使用通用 PostgreSQL 的 `DATABASE_URL` 或 PG* 配置，本地/远程、端口及账户均可指定；模板位于 `server/config/server.env.example`，见 `deploy/database/README.md`。系统级安装见 `deploy/linux/system/README.md`，用户模式迁移见 `deploy/linux/user/README.md`，均需明确操作。

## Gitea 账户只读观测

Gitea 的健康接口可能以 HTTP 424 返回失败的依赖检查。平台保留数据库、缓存等检查结果，独立查询版本；账户接口不可用时数量显示「—」，不把读取失败当作零账户。出现「数据库连接失败」时，管理员应核对 Gitea `app.ini` 中实际使用的数据库类型、地址和端口，再检查对应服务。Gitea 与平台可能使用不同的 PostgreSQL 实例，恢复平台数据库不代表 Gitea 数据库已经恢复；不要用初始化数据库或删除数据目录代替恢复服务。

「Gitea 状态」默认通过本机公开 API 列出公开可见账户；公开接口可能隐藏账户，并可能遮蔽账户状态，因此页面统一标记为「待核验」，不能据此判断账户是否正常。

如需完整账户和状态，由 **Gitea 管理员**在 Gitea 网页的用户设置 → 应用中创建仅含 `read:admin` 范围的访问令牌。将令牌单独存入平台运行用户独占、权限为 `0600` 的绝对路径文件（例如 `/home/tzr/.easymanage/config/gitea-admin-read.token`），在平台的 `server.env` 中加入 `EASYMANAGE_GITEA_ADMIN_TOKEN_FILE=该绝对路径`，并在维护窗口重启平台服务。不要把令牌写入仓库、浏览器或命令行参数。平台只向本机 Gitea 发起 GET 请求，不向网页返回令牌或邮箱。

`read:admin` 可读取 Gitea 其他管理员 API 数据，属于敏感凭据；应只授予可信任的平台运行用户，并按需轮换。平台目前没有登录鉴权，完整账户清单会对可访问该内网页面的人可见。若不接受这一范围，请保持未配置状态。账户「正常」仅根据 Gitea 的激活、禁止登录和受限标志判断，不验证密码、SSH Key 或仓库权限。
